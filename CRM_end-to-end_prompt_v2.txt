GOAL
One fully connected, deployable product with no stubs, delivering this flow:
 1. A campaign is built from a selected number of leads in waves of 100 or 200.
 2. Initial AI calls are dialled for that wave through the policy engine.
 3. Each call is classified into a scenario.
 4. After classification, leads are assigned to counsellors by lead status/scenario.
 5. The lead continues through the follow-up flow (callbacks, counsellor work, stage progression).
 6. The CRM and the voice provider reflect each other's changes in real time (new campaigns, call status,
    lead status).
 7. The whole stack deploys with Docker Compose + Caddy over HTTPS and works on any device (phone, tablet,
    desktop) from a browser.

DESIGN DECISIONS
- Source of truth: our DB owns campaigns, leads, stages, assignments. The provider ("Dograh"; the owner also
  calls it "Quadra" - same system) owns call execution and artifacts.
- CAMPAIGN MIRRORING (owner's end goal): a campaign created/started/paused/stopped in the CRM must be visible
  in the provider and the calls must be initiated by the provider. In PHASE 0, check
  packages/integrations/dograh types, fixtures and docs for provider campaign endpoints, and record the result
  in WIRING_PROGRESS.md:
  * If provider campaign endpoints exist (create/start/pause/stop/status): mirror each CRM campaign to a provider
    campaign (store provider_campaign_id on crm.campaign), push each wave's leads to it, and let the provider
    dial. The policy engine still approves every lead before it is pushed (pushing a lead = reserving a dial).
    Provider campaign/call webhooks update CRM progress. The CRM stays the source of truth for membership and
    stages.
  * If they do NOT exist: use the CRM-run design (a campaign enqueues call.dial per lead in waves, D3-I3-04)
    and tag every provider call with the CRM campaign id/name in initial_context/metadata so the campaign is
    visible on the provider side. Report this to the owner as a provider limitation.
  Either way progress is derived from call_attempt (+campaign_lead) counts, and every CRM campaign change is
  reflected in the provider and every provider change in the CRM.
- Wave size: campaign.batch_size in {100, 200}, default 100, per campaign. crm.campaign_lead may snapshot
  membership (wave_no, status, skip_reason) so membership is stable; call_attempt.campaign_id remains the link
  used for progress. A lead belongs to at most one active campaign.
- Pipeline (HANDBOOK §7.1): stages are FIXED: new, attempting, connected, interested, visit_booked, visited,
  applied, fee_paid, enrolled, lost, invalid. next_step (book_visit, fill_form, pay_fee, callback,
  counsellor_call, send_info, none) lives in lead.next_step + lead.next_step_due_at, NOT in stage. Stage moves:
  attempting when the first dial is reserved; connected when talk >15s; interested when temperature is
  Hot/Warm; visit_booked/visited from campus_visit status; applied/fee_paid/enrolled from application status;
  lost/invalid via counsellor or policy. moveStage keeps its rules (auto forward-only, never out of
  lost/invalid; manual needs a reason). Every move writes lead_stage_history.
- Scenario = derived label (pure, exhaustively tested function) from disposition + temperature + next_step +
  needs_counsellor: interested_visit, wants_form, ready_to_pay, callback_requested, needs_counsellor,
  send_info, not_interested, no_answer, invalid_number. Persist it in a nullable column on call_attempt for
  grouping/reporting. Unknown inputs never throw: no stage move, audit row, warning log.
- Classification source: analyst.run (CRM-side, LLM adapter, generateObject with zod from
  packages/contracts/analysis.ts, verbatim quotes validated as exact substrings after whitespace collapse,
  DB trigger as final guard, retry once, runs only when talk >= 15s). If the repo currently consumes a provider
  analysis.ready event, keep it only as an input that goes through the same validation and write path; it must
  not bypass quote validation or write stages directly.
- Assignment (HANDBOOK D4-I2-05 / Flow D): eligible pool = counsellors allocated to the lead's ai_agent via
  ai_agent_counsellor (fallback: active counsellors in the tenant if none allocated). Rule per tenant
  (tenant_policy.assignment_rule): round_robin (default), by_program, by_language. Skip counsellors at capacity
  (tenant_policy.counsellor_capacity, default 25 open items; add these columns, no new settings table). Applied on
  lead create AND on needs_counsellor queue items; sets lead.owner_counsellor_id / queue assignee_id. If nobody is
  eligible, leave unassigned and notify the admission head. Race-safe (FOR UPDATE SKIP LOCKED). Manual
  claim/release/reassign remain. Counsellors only see "own" leads (HANDBOOK §7.5).
- Policy engine results on dial (HANDBOOK §7.3): OUTSIDE_WINDOW / TOO_SOON -> reschedule at retryAt;
  CALL_IN_PROGRESS -> exit cleanly; SUPPRESSED / NDNC_LISTED / NO_CONSENT / CAP_REACHED / TENANT_SUSPENDED -> the
  lead is skipped in the campaign with that typed reason, shown on Lead 360; WALLET_EMPTY -> pause the campaign
  and notify. Campaign start applies static filters only (leadFilter, not in another active campaign,
  deduplicated); the policy engine re-checks every dial.
- Roles: campaigns create/start/stop = super-admin, owner/admin, admission head. Counsellors never run campaigns.
- Real-time: polling first (exists). SSE is the last optional feature phase, an addition beyond the handbook.
- Recordings: job recording.archive -> packages/integrations/storage (R2), key tenants/<tenant_id>/... per
  HANDBOOK; private, signed URLs; every playback writes recording_access_log.
- Workflow selection: dropdown via GET /agents/workflows (adapter listWorkflows exists in the handbook design;
  verify), fallback to free-text UUID with format validation.
- Env: use DOGRAH_BASE_URL and DOGRAH_PLATFORM_KEY (Appendix D). Keep GODRAH_API_BASE_URL / GODRAH_API_KEY as
  deprecated aliases that log a warning. Tenant keys live encrypted in crm.tenant_secret; a global key is a
  dev/staging fallback only and production must not depend on it.
