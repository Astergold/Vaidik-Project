## I1 — Platform / DevOps

- **Postgres roles.** Migrations run as an owner role; the app uses a separate `crm_app` role. Migration `0100` creates `crm_app`
  as `NOLOGIN` if it doesn't exist. Before the api starts, run once per environment:
  `ALTER ROLE crm_app LOGIN PASSWORD '<from password manager>';` (dev/CI create it with a password up front — see
  `packages/db/dev/init-roles.sql`).
- **Migrate step in deploy** (D2-I1-01): one-shot command, no pnpm needed in the image if you ship the dbmate binary:
  `dbmate --url "$DATABASE_MIGRATION_URL" -d packages/db/migrations --migrations-table crm.schema_migrations --no-dump-schema up`
  (the migrations table name must stay `crm.schema_migrations`).
- Owner privileges: simplest is to create `crm_app` yourself first (as `init-roles.sql` does); then the owner role only needs `CREATE` on the database. If `crm_app` doesn't exist, the owner needs `CREATEROLE` for the first run.
- `pg-boss` (Day 2) keeps its tables in its own `pgboss` schema. I2 handles the install + app-role grants in D2-I2-04; for you: the migrate step must run before api/worker start.
- Compose healthchecks: api → `GET /health`. Postgres internal network only.
- Dockerfiles are yours (`infra/`); I did not add any, to avoid clashing with D1-I1-02.
- Local dev DB is `pnpm db:up` (`packages/db/dev/docker-compose.yml`) — separate from your `infra/docker-compose.yml`; no overlap.
- CI is `.github/workflows/ci.yml` (GitHub Actions). Host isn't decided; steps are plain shell so porting is mechanical.
  D2-I1-01's image-build/deploy jobs should be **new workflow files**, not edits to `ci.yml`.

## I3 — Integrations

- **Typed DB access now:** `import { createDb, withTenant, type DB } from "@vernacular/db"`. All tables you need on Days 2–3 exist:
  `person`, `person_identifier`, `lead`, `call_attempt`, `dograh_run_raw`, `sync_cursor`, `usage_event`, `agent_tool_call`,
  `analysis`, `counsellor_queue_item`, `recording_access_log`, `campaign`, `ai_agent`, `intake_source`, `tenant_secret`.
- **`call_attempt` mapping notes**
  - Provider run id → `dograh_run_id` (unique per tenant — upsert on `(tenant_id, dograh_run_id)`).
  - Fill **both** `transcript` (json) and `transcript_text` (plain). The quote triggers read `transcript_text`.
  - Backfilled history: write final statuses (`completed|failed|no_answer|busy|rejected`). A historical run left as
    `in_progress` would hold the "one active call per lead" slot and block new dials.
  - `direction` is `outbound|inbound`.
- **`dograh_run_raw`** is an upsert mirror: `ON CONFLICT (tenant_id, dograh_run_id) DO UPDATE SET payload, fetched_at`.
- **Webhook tenant resolution:** `select * from crm.resolve_tenant_by_webhook_key($1)` works without a tenant context; then call
  `withTenant` for everything else. Keys: `tenant.webhook_key` (unguessable, generated by default).
- **Fixtures:** `packages/integrations/dograh/fixtures/` exists (empty). Mask phones.
- **Secrets:** `tenant_secret(kind, ciphertext, iv, auth_tag, key_version)` is the table; the `getSecret(tenantId, kind)` service is D2-I2-05 (Day 2). Until then use an env var in local fixtures-only tests; never commit a key.
- **Dedupe:** write identifiers with `ON CONFLICT (tenant_id, kind, value_norm) DO NOTHING` then select. Intake service from I2 (Day 3) will expose a shared `findOrCreatePerson` — use it for inbound-context (D3-I3-05) instead of re-implementing.
